# 压测报告（阶段 7）

> 对照 PRD 6.3 的性能目标。工具：`tools/loadtest`（Go 自写，零依赖，可重复执行）。

## 1. 测试口径

| 项 | 本轮实际 | PRD 6.3 约定 | 差距说明 |
|---|---|---|---|
| 环境 | Windows 11 开发机，客户端与服务端同机 | 单机 4 核 8G 分离部署 | **同机互抢 CPU，数字偏保守** |
| 数据量 | **10,000 篇已发布文章 / 100,000 条评论 / 1,000 用户**（SQL 直灌压测库） | 1 万文章 / 10 万评论 / 1 千用户 | 一致 ✓ |
| 负载 | 300–1000 请求突发 | 持续 5 分钟 | 未做长稳压测，见「已知限制」 |
| 统计 | 客户端计时（含回环网络） | 服务端中间件打点 | 含网络往返，数字略偏高 |

压测库与演示库**物理隔离**：容器 MySQL（3307）+ 独立 Meilisearch 索引 `articles_bench` + 独立后端实例（:8082），演示数据不受影响。

### 2.3 压测中发现并修复的问题

**① 列表接口 P95 超标（233ms → 39.4ms）**

10k 数据下列表 P95 达 233ms，超出 PRD 目标。EXPLAIN 显示：
`idx_status_top_published(status, is_top, published_at)` 中间夹着 `is_top`，
查询只固定 `status` 时无法利用 `published_at` 的有序性 → 扫描约 4,800 行 + filesort。

修复：`migrations/000004` 新增 `idx_status_deleted_published(status, deleted_at, published_at, id)`，
把 `deleted_at IS NULL` 放进等值前缀，排序直接走索引倒序扫描（`Backward index scan; Using index`）。
修复后 P95 39.4ms，**6 倍提升**。

**② 全量重建索引会超时（同步 → 异步）**

10,000 篇全量重建实测 **3 分 21 秒**，同步接口必然被 Nginx 60s 网关超时打成 504。
修复：`all=true` 改为异步（HTTP 202 + 后台执行，`atomic.Bool` 防并发重入），
单篇重建保持同步 200。契约同步更新（openapi 202 响应 + `accepted` 字段）。

**③ WebSocket 下行帧双层包裹（`data.data`）**

服务层拼好完整帧 `{type,data}` 后，Hub 的 `PushToUser` 又包了一层 `Frame`，
导致接收方 `f.data.message` 取不到值——在线推送实际是坏的。
修复：`PushToUser` 识别完整帧只补 `ts`，裸数据才包 `Frame`。

## 3. 已知限制

1. **未做 5 分钟长稳压测**：PRD 口径要求持续 5 分钟。本轮为 300–1000 请求的突发压测，
   足以暴露查询计划与锁问题，但内存泄漏、连接池耗尽这类长稳问题未覆盖。
2. **客户端与服务端同机**：互相争抢 CPU，吞吐数字偏保守；P95 偏差方向不确定。
3. **搜索压测样本较小**（10 并发 500 请求）：Meilisearch 在本机与 MySQL 争 IO。
4. 压测数据（bench-*) 留在压测库（容器 3307）中，演示库（3306）不受影响；复测前需确认压测实例在跑。
